# 大模型辅助开发使用说明

## 使用工具与目的

本项目开发过程中使用 Codex / ChatGPT 作为编程辅助工具，主要用于阅读和归纳需求、检查数据模型与业务规则的一致性、生成阶段性实现草案、补充测试、定位编译与运行错误，以及整理交付文档。

大模型不是项目的独立决策者，也不是未经检查地一次性生成整个系统。课程设计的需求边界、业务规则、数据库变更和阶段验收结论均由人工确认。

## 分阶段协作流程

1. 先完整阅读课程要求与需求设计，形成阶段0设计基线。
2. 将开发拆分为基础框架、数据库、认证权限、俱乐部、联赛、比赛、场馆、票务、连坐、订单、支付、退票、检票、统计和交付等阶段。
3. 每阶段只实现约定范围，完成后执行编译、测试和真实流程验证，再由人工确认是否进入下一阶段。
4. 当实现需要修改已确认的数据结构时，大模型先报告冲突和最小修正方案，暂停编码，获得人工确认后才同步修改数据库、字段字典和代码。
5. 最终阶段在隔离 MySQL 上从空库初始化，执行全量测试、真实 JAR HTTP 流程、前端构建和数据一致性查询。

阶段开发历史中曾实现独立CHECKER检票模块。当前正式提交版本固定为 `USER`、`CLUB`、`EVENT_ADMIN`、`ADMIN` 四类角色，检票模块不属于本次最终验收范围；相关代码和历史测试保留用于版本追溯，不据此声称功能不存在。

## AI与人工职责

AI辅助完成：需求梳理、代码与SQL草案、重复性实现、静态检查、测试用例建议、错误定位、接口联调和文档整理。

人工负责：确认需求不被擅自简化、批准数据库基线及最小变更、决定阶段范围、审查业务口径、提供运行权限、验收实际结果并承担最终提交责任。

## 质量控制

- 后端保持 Controller、Service、Mapper 分层，数据权限和事务规则集中在Service。
- 对当前正式范围内的认证、俱乐部、联赛、比赛、场馆、票务、连坐、订单、支付、退票和统计执行自动化测试。
- 对锁座、支付和退票执行数据库集成及并发竞争测试；旧CHECKER检票测试单独归档，不计入当前默认测试基线。
- 使用真实构建产物完成购票支付、购票退票、CLUB账号绑定启用和EVENT_ADMIN统计HTTP链路，而非仅依赖MockMvc。
- 每次数据库核心冲突都采用“发现冲突 → 暂停 → 人工确认 → 最小修正 → 重新验证”的方式处理。

## 优势与风险

优势是能快速覆盖大量重复代码和测试场景，帮助发现跨模块字段、状态机、数据权限和事务一致性问题，并持续维护文档与实现的一致性。

风险包括对需求理解偏差、生成代码存在缺陷、过度设计、依赖版本或环境判断错误，以及测试看似通过但未真正连接数据库。项目通过阶段边界、人工确认、隔离数据库、`Skipped = 0`、真实HTTP验证和敏感信息检查降低这些风险。

## 使用结论

本项目采用“AI辅助分析、生成、检查；人工确认需求和关键设计；通过分阶段验收、数据库测试与真实流程验证控制质量”的开发方式。
