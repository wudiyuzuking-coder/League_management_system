# 更新日志

本文由原《待修改事项.md》和《版本待修改事项.md》合并整理而来，用于记录项目在两轮讨论和联调过程中形成的需求更新、设计调整和运行说明修订。本文是对两份待修改事项的归纳总结，不逐条保留旧待办表述；本次实际测试发现的问题单独记录在《本次测试问题汇报.md》中。

## 第一次更新：角色、登录与基础演示流程调整

### 运行与兼容

- 确认本机 MySQL、前后端端口和数据库状态是课程演示启动前必须检查的基础项。
- 发现旧版浏览器缓存可能保留旧角色值，导致登录页和角色首页之间出现异常跳转；需要对旧 Token、旧角色缓存和不支持的角色值做清理。
- 运行脚本不应写死个人电脑路径、固定端口或本机数据库配置，应改为通过环境变量或本机配置注入。
- README 需要补充 Windows 环境下 SQL 导入的兼容写法，避免部分 MySQL 客户端无法执行 `mysql -e "source ..."`。

### 角色与权限

- 注册体系收口为普通用户和俱乐部负责人公开注册；赛事管理员和系统管理员不再作为普通公开注册入口。
- 登录页增加身份选择，用户需要明确以普通用户、俱乐部负责人、赛事管理员或系统管理员身份登录。
- 赛事管理员和系统管理员登录时，除手机号和密码外，还需要提交对应工号，并由后端校验手机号、密码、身份和工号是否匹配。
- 赛事管理员负责赛季创建、报名处理、赛程确认、比赛发布、赛果维护和赛事营收统计等赛事运营功能。
- 系统管理员负责用户管理、内部人员管理、俱乐部管理、俱乐部负责人审核、账号启停和争议赛果审核等系统管理功能。
- 删除检票员作为当前正式角色的要求，相关历史模块仅作为版本追溯内容保留。

### 用户与购票流程

- 用户买票后的退票入口收口到“我的订单”，不再在用户侧单独设置退票一级入口，也不在电子票页面重复展示已退票分类。
- 用户查看比赛时，需要能够进入主队、客队的俱乐部详情，了解球队信息后再购票。
- 比赛详情需要突出比赛时间、场馆地址、VIP/普通票价和余票；票价应明显展示，避免把偏后台的座位范围、总票数、最大连坐数等信息直接展示给用户。
- 购票开放时间由赛季报名截止时间自动推导：报名截止后的次日 20:00 开放买票；每场比赛开赛前 1 小时停止售票。

### 俱乐部负责人流程

- 俱乐部负责人注册时需要提交负责人信息和俱乐部名称，账号注册后等待系统管理员审核。
- 审核通过后，应直接创建该俱乐部并绑定当前负责人，不再提供“关联已有俱乐部”的选项。
- 每个俱乐部应有且仅有一个负责人，俱乐部列表和详情页需要展示负责人姓名、手机号和账号状态。

## 第二次更新：数据库文档、系统时间与扩展业务完善

### 环境与数据库说明

- README 需要补充 MySQL 未加入 PATH 时的处理方式，可通过完整 MySQL 客户端路径执行导入命令。
- README 需要补充输入重定向导入 SQL 的方案，提升 Windows 环境兼容性。
- 项目需要提供 `.env.example`，明确后端 `dev` Profile 所需环境变量，包括数据库连接、JWT 密钥、演示密码初始化和上传目录等配置。
- `test-data.sql` 需要说明只适合空库、隔离开发库或专用测试库；已有数据环境导入前必须备份。
- 前端启动依赖 Node.js 20.19+、22.12+ 或更高兼容版本，README 应提示先检查 `node -v` 和 `npm -v`。
- 前端中文内容应统一保存为 UTF-8，避免课程演示时出现乱码。

### 账号、资料与头像

- 登录方式调整为选择身份后使用手机号登录；同一个手机号可以在合规前提下注册多个不同身份，系统内部通过账号 ID、身份、手机号和必要工号共同区分账号。
- 用户名允许重复，允许注册后修改，不再作为登录唯一凭证；前端文案统一使用“用户名”，不再使用“昵称”。
- 注册后用户可以修改用户名和头像。
- 账号资料入口不作为一级菜单展示，改为点击头像或用户名后进入；普通用户不要求维护真实姓名，购票实名信息改为单独管理“预填购票人”。

### 统一演示时间系统

- 系统需要建立独立的“当前时间”机制，所有涉及时间判断的业务使用统一系统时间，而不是直接使用电脑真实时间。
- 普通用户、俱乐部负责人、赛事管理员和系统管理员均可以调整当前时间，调整后对全系统即时生效。
- 时间调整用于演示赛季报名、比赛开始、购票开售、退票截止、赛后比分录入等时间敏感流程。
- 时间调整应记录操作日志，包括调整人、调整前时间、调整后时间和操作时间。
- 倒计时、比赛剩余天数、报名截止、售票开始/结束、退票截止和比分录入限制均应接入统一系统时间。

### 用户端信息链路

- 用户端需要形成“赛季 -> 赛程 -> 比赛详情 -> 俱乐部信息 -> VIP/普通票价 -> 购票”的完整展示链路。
- 俱乐部详情页需要展示俱乐部基础信息、球员名单、教练信息、积分或近期战绩。
- 俱乐部详情页还应展示该俱乐部相关比赛，并突出最近比赛距离系统当前时间还有几天。
- 比赛详情页需要展示比赛时间、剩余票数、场馆地址、VIP/普通票价和余票。开售时间只在未开售时展示；停售时间不对用户展示。

### 俱乐部负责人报名流程

- 俱乐部负责人审核通过后，可以查看当前可报名赛季并提交报名。
- 俱乐部只能报名时间不冲突的赛季；如赛季时间冲突，需要提示不可报名原因。
- 报名前需要填写主场场馆信息，场馆按东、西、南、北四个看台组织，每个看台分为内场 VIP 和外场普通两个区域。
- 主场信息需要包含城市、场馆名称、场馆地址、VIP/普通定价和场地结构数据；场地结构先填写每区排数、长边每排座位数和宽边每排座位数 3 项，由系统按 8 个票区规则计算容量。
- 球员信息在“人员管理”中维护，包括姓名、位置、号码、出生年、国籍和首发/替补/离队状态；位置限定为前锋、中场、后卫、守门员。
- 系统根据统一当前时间和出生年计算年龄，只显示年龄，不直接显示生日。
- 报名要求为有且仅有 1 名首发门将、刚好 11 名首发球员、替补不超过 7 人；教练要求为有且仅有 1 名现役主教练、至多 2 名现役副教练，年龄展示规则与球员一致。
- 俱乐部负责人需要能够查看已报名赛季和已安排比赛，并显示最近比赛倒计时。

### 赛事管理员功能

- 赛事管理员账号应遵守管理账号安全规则，注册或创建后需要符合启用条件才能获得赛事管理权限。
- 赛事管理员可以创建赛季，设置球队数量上限，单赛季球队数量上限不得超过 20 支。
- 创建赛季时只需要提供赛季开始日期和参赛队伍上限；开始日期必须晚于当前系统时间至少 1 个月，队伍上限最小 2 队、最大 20 队。
- 赛季注册后，下一个 20:00 开放俱乐部报名；报名截止时间为首场比赛开始前 15 天 19:59，报名截止后的次日 20:00 开放买票。
- 报名截止时间到达或报名球队数量达到上限后，系统自动安排赛程。
- 赛程采用主客场双循环，同一支球队两场比赛之间至少间隔 6 天。
- 系统生成赛程后，由赛事管理员点击确认即可完成审核。
- 赛后比分只能在比赛当天及以后录入，未到比赛日期不得录入。
- 系统需要为赛事管理员提供赛后比分录入提醒，提示及时维护比赛结果。
- 票务规则按系统固定规则执行：场馆信息由俱乐部填写，退票无需人工审核，开赛前 7 天以外全额退款，开赛前 7 天内收取 50% 手续费，开赛前 1 小时停止售票。

### 系统管理员功能

- 系统默认保留一个初始系统管理员账号，用于首次进入系统和创建后续管理账号。
- 已有系统管理员负责预先登记新的赛事管理员和系统管理员准入信息。
- 登记新管理员时，需要填写管理员类型、手机号、姓名和 4 位工号数字，系统根据类型自动补全 `EA` 或 `SA` 前缀。
- 新的赛事管理员或系统管理员首次登录时，需要输入正确手机号、姓名和工号，且必须与系统管理员预先登记的信息完全对应。
- 信息匹配成功后，该管理员设置密码并完成首次启用；如果姓名、手机号和工号不匹配，或未被预先登记，应提示无权限。
- 赛事管理员工号格式为 `EA` 加 4 位数字，例如 `EA0001`。
- 系统管理员工号格式为 `SA` 加 4 位数字，例如 `SA0001`。
- 系统需要校验管理人员工号格式和唯一性。

### 启动问题提示

- 后端启动说明需要补充常见错误排查，例如数据库连接失败、JWT_SECRET 未设置、端口 8080 被占用等。
